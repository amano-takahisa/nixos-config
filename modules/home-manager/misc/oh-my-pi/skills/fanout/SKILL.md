---
name: fanout
description: docs/plans/ の計画から、依存が解決済みかつ変更ファイルが重ならない未完了タスク群を、implementer/reviewer サブエージェントで並列実装・レビュー・コミットする。
---

`plan` スキルが作成した実装計画書 (`docs/plans/NNNN-*.md`) から並列実行可能なタスク群を
抽出し、`implementer` サブエージェントへ隔離ワークスペース上で並列実装させ、
`reviewer` サブエージェントの判定を経て親がコミットするまでを行ってください。

逐次進行には `next` スキルを使う。`fanout` は「複数タスクを同時に消化したい」場合にのみ使う。

> **コンテキストコストについて (重要)**: 親が担うのは仕様ファイル生成・タスク起動・
> 報告集約・コミット・進捗更新という**機械的な調整**であり、推論は不要。実行前に確認・案内する:
>
> - grill-me / plan と同一セッションで続けて呼ばれた場合、親コンテキストが肥大している。
>   計画書は自己完結しているので、`/clear` して新セッションから実行するよう提案する。
> - サブエージェントのモデルは implementer / reviewer の frontmatter
>   (`model: "@worker"` / `"@review"`) で固定されており、親のモデルを切り替える必要はない。
>   親は調整役のままでよい。

## 前提 (oh-my-pi の分離実行)

- 各 implementer は `isolated: true` で起動し、spawn ごとの独立ワークスペース
  (`~/.omp/wt/<id>/...`) で作業する。手動の `git worktree` 運用は不要。
- 完了時、そのワークスペースの変更は patch として**親の作業ツリーに自動適用**される
  (`task.isolation.apply: true`)。同時にブランチ `omp/task/<name>` が作られる。
- したがって「マージ」に相当する操作は存在せず、親が行うのは**コミットするか revert するかの
  判断**だけになる。
- isolated なサブエージェントは完了後に復帰できない (ワークスペースは適用後に破棄される)。
  差し戻しは**新しい spawn** で行う。

## 手順

### 1. 計画とタスクを選ぶ

- 引数で番号が指定されていればその計画を、なければ `docs/plans/` からステータスが
  `進行中` の計画を選ぶ (進行中が複数ある場合のみ `ask` ツールで確認する)。
- 未完了タスク (`- [ ]`) のうち、「依存に列挙されたタスクが全て `[x]`」かつ
  「書き込み対象の変更ファイルglob同士が互いに素 (読み取り専用注記は除外)」であるものを
  抽出する。1件しか抽出できない場合は `next` の利用を提案し、ユーザーの意向を確認する。

### 2. 親ツリーを clean な状態にする

`git status --porcelain` を確認し、未コミットの変更があれば**先にコミットするか stash する**
ようユーザーに確認する。patch は現在のコミット (HEAD) を基点に適用されるため、未コミットの
変更が残っていると却下時の巻き戻しができなくなる。

### 3. タスク仕様ファイルを生成しコミットする

抽出した各タスクについて、計画書・関連ADRから自己完結した仕様ファイルを
`docs/plans/NNNN-tasks/<タスク番号>.md` に生成する。内容:

- タスク内容・受け入れ条件 (計画書から転記)
- 関連ADRの決定事項のうちこのタスクに効く部分の要約
- 変更してよいファイルの明示的リスト (読み取り専用の共有ファイルがあれば明記)
- 検証コマンド。デフォルトはリポジトリ統一の `nix develop -c check` (ADR-0006参照)。
  計画書に別のコマンドが明記されていればそちらに従う。devShellに `check` が未定義の
  リポジトリでは、fanout を進める前にユーザーへ報告し、検証コマンドを確認する

生成したファイルを `git add` して main に直接コミットする (監査証跡として履歴に残す)。

> この仕様ファイルは監査証跡であり、実行の正しさを担保する主経路ではない。
> サブエージェントは親の会話履歴を継承せず、隔離ワークスペースは HEAD から作られるため、
> 次のステップで仕様の全文を委譲プロンプト (`context` と各 item の `task`) にも埋め込むこと。

### 4. 実行前承認

並列実行するタスク一覧 (タスクID・内容・変更ファイル・割り当てる agent 名) をユーザーに
提示し、承認を得る。並列数の固定上限は設けないが、`task.maxConcurrency` (既定 32) が
セッション全体の上限として効くため、そのつどタスク量と使用量を見て判断する。

### 5. implementer へ並列委譲する

承認されたタスクを、**1回の `task` 呼び出し**で batch 形式として並列起動する。

- `context` (共有前提。全サブエージェントの system prompt に注入される):
  - リポジトリ規約: 開発ツールは `flake.nix` + direnv 経由のものを使用し、
    グローバルの同名コマンドを使わないこと。`flake.nix` は編集しないこと。
  - 検証コマンド (デフォルト `nix develop -c check`)
  - 関連ADRの決定事項の要約
  - 報告フォーマット: 変更ファイル一覧・検証コマンドの合否・仕様からの逸脱のみ。
    差分全文や検証ログの全文は貼らないこと
  - 変更してよいのは各タスクの「変更ファイル」に列挙された範囲のみであること
  - 自分の作業ディレクトリは spawn ごとの隔離ワークスペースであり、親の作業ツリーを
    直接操作してはならないこと
  - **リポジトリルートは `pwd` を指す。**ファイル操作は `pwd` 配下の相対パスで行い、
    `pwd` の外を指す絶対パスへ書き込まないこと。タスク仕様に現れるパスはすべて
    `pwd` からの相対パスとして解釈すること
- `tasks[]`: タスクごとに 1 item
  - `name`: `impl-<タスク番号>` (例: `impl-1-1`)。隔離ブランチ名 `omp/task/<name>` が
    この名前から決まるため、省略せず明示する
  - `agent`: `implementer`
  - `task`: タスク仕様の全文 (タスク内容・受け入れ条件・変更してよいファイル一覧・
    検証コマンド・仕様ファイルのパス `docs/plans/NNNN-tasks/<タスク番号>.md`)
  - `isolated`: `true`

結果は各サブエージェントの完了時に自動で届く。**到着まで他の作業を始めないこと。**

### 6. reviewer へ委譲する

各タスクについて、`reviewer` を **1件ずつ順番に** spawn する。全員が同じ親ツリー
(適用済み patch) を見るため、並列に走らせると検証コマンドが互いに干渉する。
reviewer は `isolated` を付けず親ツリーで実行させる (隔離ワークスペースは HEAD から
作られるため、適用済み patch が見えない)。

reviewer への `task` に含めるもの:

- 対象タスクの受け入れ条件・変更してよいファイル一覧 (読み取り専用の共有ファイルも明記)
- 関連ADRの決定事項の要約
- 検証コマンド (デフォルト `nix develop -c check`。タスク仕様に別のコマンドがあればそちら)
- `git diff -- <対象ファイル>` で自分の担当ファイルの差分だけを確認すること
- 「承認」または「却下 (理由・修正指示を明記)」のいずれかで報告すること。
  コードの編集は行わないこと
- 報告は簡潔に。判定・検証コマンドの合否・却下時の具体的な修正指示のみを返し、
  検証ログや差分の全文は貼らないこと
- 他タスクの patch が同じ作業ツリーに適用されているため、検証コマンドの失敗が
  自分の担当ファイルに起因するかどうかを切り分けて報告すること

### 7. 判定と確定

- **承認 かつ 検証コマンド成功**の場合:
  1. 計画書のチェックボックスを `- [x]` にし、「作業メモ」に日付付きで実施内容・
     得られた知見を追記する。複数タスクを1ラウンドで回した場合も、ラウンド分の
     メモをここでまとめて書いてよい。
  2. `commit` スキル (`skill://commit`) の手順で、**そのタスクの変更と上記の計画書
     更新を1コミットに**まとめてコミットする。計画書だけのコミットを作らないこと
     (進捗の記録はタスクの一部であり、後始末ではない)。
  3. `git branch --list 'omp/task/*'` で残った隔離ブランチを確認し、対応する変更が
     コミット済みのブランチを削除する (`git branch -D omp/task/<name>`)
- **却下**の場合: 対象タスクの変更を親ツリーから revert してから、修正指示を添えて
  implementer を **新規に spawn** し直す (差し戻しは1往復まで):
  - 追跡ファイル: `git checkout HEAD -- <変更ファイル>`
  - 新規ファイル: `rm -f <新規ファイル>`
  - revert してから spawn することで patch の基点が HEAD に揃い、再 spawn の patch が
    タスク実装全体として正しく適用される
  - 再度 reviewer にかけ、2回目も却下ならコミットせず親 (ユーザー) にエスカレーションする
- **検証コマンドが失敗**した場合は reviewer の承認に関わらずコミットしない。
  失敗内容を添えてユーザーにエスカレーションする。

## 例外時のルール

- **implementer が同一タスクで2回失敗した場合**: リトライを続けず、親が引き取るか
  ユーザーに報告する。
- **仕様ファイルが隔離ワークスペースに見当たらないと implementer が報告した場合**:
  プロンプト本文の埋め込み内容で実装を継続してよい。実装内容とプロンプトの整合を親が確認する。
- **patch が適用されなかった / 適用に失敗した場合**: `agent://<id>` の出力と
  `task.isolation` の設定 (`enabled` / `apply` / `merge`) を確認し、原因を報告する。
  `task.isolation.merge: branch` を使っている場合は、`omp/task/<name>` ブランチの
  cherry-pick が必要になる。
- **想定外のファイルが親ツリーで変更されていた場合**: どのタスクの patch に由来するかを
  `git diff` と各 implementer の報告で突き合わせ、範囲外変更として報告する
  (implementer は隔離ワークスペースで動くため、親ツリーを直接壊すことはない)。
- **ADRの前提が崩れた場合**: 黙って逸脱させず、`adr` スキルでの ADR 更新を提案する。

## 全タスク完了時

計画書の全タスクが完了したら `next` スキルと同様、計画のステータス更新や
関連ADRの `承認済み` への更新提案を行う。
