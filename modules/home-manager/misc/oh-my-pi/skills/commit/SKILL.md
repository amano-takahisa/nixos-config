作業ツリーの変更を以下のルールに従ってコミットしてください。
引数でコミット対象の説明が与えられていれば、それを対象にする。

## 手順

1. **現状を把握する**: `git status` と `git diff` (staged / unstaged 両方) で全変更を
   確認する。
2. **規約を学ぶ**: `git log --oneline -20` で直近のコミットメッセージのスタイル
   (言語、conventional commits の有無、プレフィックス、長さ) を確認し、それに合わせる。
3. **論理単位に分割する**: 「1つの関心事 = 1コミット」になるよう変更をグループ分けする。
   機能変更とリファクタリング、無関係なファイルの変更は別コミットにする。タスクや依頼と
   無関係な変更 (他作業の残骸など) はコミットに含めず、その存在を報告する。
   - **計画書の進捗更新 (`docs/plans/` のチェックボックス・作業メモ) は、そのタスクの
     変更と同じコミットに入れる**。進捗の記録はタスクの一部であり、後始末ではない。
     進捗更新だけのコミットを作らないこと (fanout が dispatch 前に切るタスク仕様
     ファイルのコミットだけは例外: 仕様は着手前に存在する必要がある)。
   - コミット済みファイルに**コミットハッシュを書かない**。ハッシュはそれを含む
     コミットより前に確定できず、「ハッシュを綴り直すだけのコミット」を生む。
4. **確認の要否を判断する**:
   - 変更全体が明らかに1つの作業のまとまり (例: `next` スキルの1タスク分、
     ユーザーが直前に依頼した一連の変更) → **確認なしでそのままコミットする**
   - 変更が複数の関心事に分かれる、または対象に迷いがある →
     分割案 (各コミットの対象ファイルとメッセージ) を提示し、承認を得てからコミットする
5. **コミットする**: グループごとに対象ファイルを明示的に `git add` してコミットする。
   `git add -A` や `git add .` は使わない。
6. **結果を報告する**: 作成したコミットを `git log --oneline` で提示する。

## 安全ルール

- **push はしない** (ユーザーが明示的に依頼した場合のみ)
- `--amend` や rebase による履歴改変は、ユーザーの明示的な依頼なしに行わない
- pre-commit フックが失敗したら、`--no-verify` で回避せず、失敗内容を報告する
- 秘密情報らしきもの (鍵・トークン・パスワード) が diff に含まれる場合は
  コミットせずに警告する
- `flake.nix` を変更に含める場合は、コミット前にユーザーの確認を取る
