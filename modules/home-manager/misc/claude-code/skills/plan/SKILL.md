実装計画書を以下のルールに従って管理してください。

## 基本ルール

- 保存先: プロジェクトルートの `docs/plans/`
- ファイル名: `NNNN-kebab-case-title.md`（番号は4桁ゼロ埋め、既存最大+1）
- 記述言語: 日本語
- 計画書は `next` スキルが1タスクずつ消化する前提で書く

## コマンド判定

- `list` または `ls` → `docs/plans/` 内の計画を番号・タイトル・ステータス・進捗（完了タスク数/全タスク数）で一覧表示
- 数字のみ → 指定計画を表示
- それ以外（タイトルやADR番号、引数なし）→ **新規計画作成**

## 新規計画作成手順

1. **材料を集める**: `docs/adr/` の関連ADR（引数で指定されたもの、または直近の
   会話に関係するもの）と、リポジトリの現状コードを読む。ここまでの会話
   （grill-me等での議論）で判明している内容はそのまま使い、再質問しない。
2. **不足があれば聞く**: ゴールやスコープが曖昧な場合のみ、AskUserQuestion で
   一つずつ確認する。実装の詳細はタスク側に委ね、ここでは聞きすぎない。
3. **タスクに分解する**: 以下の粒度ルールを守る:
   - 各タスクは **1コミット〜1PRで完結し、単独で検証可能** な大きさにする
   - 各タスクに受け入れ条件（何ができたら完了か）を1〜2行で書く
   - 依存関係のある順に並べ、意味のある区切りでマイルストーンに分ける
   - 「テストを書く」を独立タスクにせず、各タスクの受け入れ条件に含める
   - `fanout` スキルによる並列実行を前提に、タスク間で書き込み対象のファイル
     所有権が重ならないように分割する（下記「変更ファイル」「依存」を参照）
4. **ドラフトを提示して承認を得てから** ファイルを作成する

### 計画書テンプレート

```markdown
# PLAN-NNNN: タイトル

## ステータス

進行中（YYYY-MM-DD 開始）

## 関連ADR

- [ADR-NNNN: タイトル](../adr/NNNN-title.md)

## ゴール

<!-- この計画が完了したとき何ができるようになっているか（2〜3行） -->

## スコープ外

- <!-- 今回やらないと決めたこと -->

## タスク

### マイルストーン 1: 名前

- [ ] 1-1: タスク内容
  - 受け入れ条件: <!-- 何ができたら完了か -->
  - 変更ファイル: <!-- glob。例: src/foo/**, src/types.ts（読み取りのみ） -->
  - 依存: <!-- 依存タスクID。カンマ区切り。なければ「なし」 -->
- [ ] 1-2: タスク内容
  - 受け入れ条件: ...
  - 変更ファイル: ...
  - 依存: 1-1

### マイルストーン 2: 名前

- [ ] 2-1: ...

## 作業メモ

<!-- next スキルが実装中に得た知見・変更した前提をここに追記する -->
```

### 「変更ファイル」「依存」フィールド

- **変更ファイル**: そのタスクが書き込む対象を glob で列挙する。読み取りのみ
  参照する共有ファイル（型定義・スキーマ等）は `（読み取りのみ）` と注記し、
  書き込み対象とは区別する。
- **依存**: 先に完了している必要があるタスクIDをカンマ区切りで書く。ない場合は
  「なし」と明記する。
- **並列実行可否の判定基準**（`fanout` スキルが使用）: 「依存タスクが全て
  完了している」かつ「書き込み対象の変更ファイルglob同士が互いに素である」
  タスク群は並列実行可能とみなす。読み取り専用の注記が付いたファイルは
  この判定から除外する（複数タスクが同じファイルを読み取り専用で参照しても
  競合とはみなさない）。

## ステータス

計画のステータスは `進行中` / `完了` / `中止` のいずれか。全タスク完了時に
`完了（YYYY-MM-DD）` に更新する。中止時は理由を追記する。
