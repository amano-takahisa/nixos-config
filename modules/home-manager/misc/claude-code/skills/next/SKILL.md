実装計画書（`plan` スキルが作成した `docs/plans/NNNN-*.md`）を1タスクずつ消化してください。

## 手順

1. **計画を選ぶ**: 引数で番号が指定されていればその計画を、なければ
   `docs/plans/` からステータスが `進行中` の計画を選ぶ。進行中が複数ある
   場合のみ、AskUserQuestion でどれを進めるか確認する。
2. **タスクを特定する**: 計画書の先頭から最初の未チェックタスク（`- [ ]`）を
   取る。着手前に「どのタスクをやるか」と受け入れ条件をユーザーに一言で伝える
   （確認は求めず、そのまま進める）。
3. **前提を確認する**: 関連ADRと計画の「作業メモ」を読み、前回までの知見を
   引き継ぐ。タスクの前提がすでに崩れている場合は実装せず、ユーザーに報告する。
4. **実装する**: 受け入れ条件を満たすように実装する。テストが受け入れ条件に
   含まれる場合はテストも書く。
5. **検証する**: テストを実行し、`verify` スキルが使える変更なら呼び出して
   実際の動作を確認する。受け入れ条件を一つずつ照合する。
6. **進捗を記録する**: 検証が通ったら:
   - 計画書のチェックボックスを `- [x]` にする
   - 実装中に得た知見・変更した前提があれば「作業メモ」に日付付きで追記する
   - `commit` スキルを呼び出してタスク単位でコミットする（1タスク分の変更で
     あることが明確なので、通常は確認なしでコミットされる）

## 例外時のルール

- **タスクが大きすぎた場合**: 実装を進める前に、計画書上でタスクを分割して
  から着手する（分割した旨をユーザーに伝える）。
- **ADRの前提が崩れた場合**: コードを黙って決定から逸脱させない。何が
  崩れたかを報告し、`adr` スキルでのADR更新（差し替え・廃止）を提案する。
- **検証が通らない場合**: チェックボックスは更新しない。失敗内容をそのまま
  報告する。

## 全タスク完了時

- 計画書のステータスを `完了（YYYY-MM-DD）` に更新する
- 関連ADRのうち `提案中` のものがあれば、`承認済み` への更新を提案する
- 実装を通じて得た知見でADRの追記・更新が必要なものがないか確認する
