`plan` スキルが作成した実装計画書（`docs/plans/NNNN-*.md`）から、並列実行可能な
タスク群を抽出し、`implementer`/`reviewer` サブエージェントで実装・レビュー・
自動マージまでを行ってください。関連ADR: [ADR-0004](../../../../../../docs/adr/0004-llm-fanout-pipeline.md)、
[ADR-0005](../../../../../../docs/adr/0005-fanout-auto-merge-without-human-approval.md)。

逐次進行には `next` スキルを使う。`fanout` は「複数タスクを同時に消化したい」
場合にのみ使う。

## 手順

### 1. 計画とタスクを選ぶ

- 引数で番号が指定されていればその計画を、なければ `docs/plans/` からステータスが
  `進行中` の計画を選ぶ（進行中が複数ある場合のみ AskUserQuestion で確認する）。
- 未完了タスク（`- [ ]`）のうち、「依存に列挙されたタスクが全て `[x]`」かつ
  「書き込み対象の変更ファイルglob同士が互いに素（読み取り専用注記は除外）」
  であるものを抽出する。1件しか抽出できない場合は `next` の利用を提案し、
  ユーザーの意向を確認してから続ける。

### 2. タスク仕様ファイルを生成しコミットする

抽出した各タスクについて、計画書・関連ADRから自己完結した仕様ファイルを
`docs/plans/NNNN-tasks/<タスク番号>.md` に生成する。内容:

- タスク内容・受け入れ条件（計画書から転記）
- 関連ADRの決定事項のうちこのタスクに効く部分の要約
- 変更してよいファイルの明示的リスト（読み取り専用の共有ファイルがあれば明記）
- 検証コマンド（テスト・`nix flake check` 等の実行方法）

生成したファイルを `git add` してmainに直接コミットする（監査証跡として履歴に残す）。

> **注意（ADR-0004参照）**: `isolation: worktree` のworktreeは、Agent呼び出し
> 時点のHEADではなく、セッション開始時点のコミットから分岐することが実測で
> 確認されている。そのためこの仕様ファイルは監査証跡であり、実行の正しさを
> 担保する主経路ではない。次のステップで、仕様ファイルの内容を委譲プロンプト
> 本文にも全文埋め込むこと。

### 3. 実行前承認

並列実行するタスク一覧（タスクID・内容・変更ファイル）をユーザーに提示し、
承認を得る。並列数に固定上限は設けず、そのつどタスク量や使用量を見て判断する。

### 4. implementerへ並列委譲する

承認された各タスクについて、`Agent` ツールで `subagent_type: implementer` を
1タスク1呼び出しで並列起動する（複数タスクがあれば1メッセージ内で複数の
Agent呼び出しを行う）。プロンプトには次を**全文埋め込む**（ファイルパス参照
だけに頼らない):

- **（安全ルール・必須）** 「作業開始前に必ず `pwd` と
  `git rev-parse --show-toplevel` を実行し、現在の作業ディレクトリが自分に
  割り当てられた独立worktreeであることを確認すること。メインリポジトリの
  パス（`<リポジトリルートの絶対パス>`）であってはならない。以降のすべての
  git操作・ファイル操作はこのworktreeディレクトリの外に出て行ってはならない」
  （実地検証で、この指示を省いた結果implementerが親のメイン作業ディレクトリ
  側でブランチ操作・マージを実行してしまう事故が発生している。ADR-0004参照）
- タスク内容・受け入れ条件
- 変更してよいファイルの明示的リスト
- 検証コマンド
- 手順として明示する: 「まず `git checkout -b task/NNNN-X` で新しいブランチを
  作成する（`isolation: worktree` が自動で割り当てるブランチ名は使わない）。
  実装後、対象ファイルのみをコミットする。」
- 「`docs/plans/NNNN-tasks/<タスク番号>.md` が存在すれば読み合わせに使ってよいが、
  存在しない場合や内容が矛盾する場合はこのプロンプトの内容を優先し、その旨を
  報告に含める」

各implementerの完了報告（ブランチ名・コミットハッシュ・差分・検証結果）を待つ。

### 5. reviewerへ委譲する

各タスクについて、`Agent` ツールで `subagent_type: reviewer` を起動する前に、
**該当implementerのworktreeを削除する**（`git worktree remove`。ブランチ自体は
残す）。同一ブランチは複数worktreeで同時にチェックアウトできないため、
reviewer側で `task/NNNN-X` をチェックアウトできるようにする必要がある。

reviewerへのプロンプトには次を含める:

- **（安全ルール・必須）** implementer委譲時と同じ安全ルールを明記する:
  「作業開始前に必ず `pwd` と `git rev-parse --show-toplevel` を実行し、
  現在の作業ディレクトリが自分に割り当てられた独立worktreeであることを
  確認すること。メインリポジトリのパスであってはならない。対象ブランチの
  チェックアウトを含め、以降のすべてのgit操作はこのworktreeディレクトリの
  外に出て行ってはならない」
- 対象ブランチ名（`task/NNNN-X`）と、まずそのブランチをチェックアウトすること
- タスクの受け入れ条件・変更してよいファイルの範囲・関連ADRの決定事項の要約
- 「`git diff main...task/NNNN-X` で差分を確認し、範囲外のファイルを変更して
  いないか、受け入れ条件を満たしているかを確認せよ」
- 「自分のworktreeで検証コマンド（`nix flake check` を含む）を実行し、結果を
  確認せよ」
- 「結果は『承認』または『却下（理由・修正指示を明記）』のいずれかで報告せよ。
  コードの編集は行わないこと」

### 6. 判定とマージ

- **承認 かつ 検証コマンド成功**の場合のみ、親が確認なしで
  `git merge --no-ff task/NNNN-X` でmainに取り込む。マージ後、reviewer側の
  worktreeとブランチ (`task/NNNN-X`)、worktree作成時に自動生成された
  `worktree-agent-*` ブランチを削除する。
- **却下**の場合、reviewerの指摘内容を添えて、`SendMessage` で**同一の
  implementerインスタンス**を再開し、修正を依頼する（差し戻しは1往復まで）。
  再度reviewerにかけ、2回目もNGならマージせず親（ユーザー）にエスカレーション
  する。
- **検証コマンドが失敗**した場合はreviewerの承認に関わらずマージしない。
  失敗内容を添えて親にエスカレーションする。

マージが完了したタスクごとに:

- 計画書のチェックボックスを `- [x]` にする
- 「作業メモ」に日付付きで実施内容・得られた知見を追記する
- 上記の計画書更新のみを親がコミットする（サブエージェントには計画書を
  触らせない）

## 例外時のルール

- **implementerが同一タスクで2回失敗した場合**: リトライを続けず、親が
  引き取るかユーザーに報告する。
- **仕様ファイルがworktree内に見当たらないとimplementerが報告した場合**:
  プロンプト本文の埋め込み内容で実装を継続してよい（手順4の全文埋め込みが
  ここで効く）。実装内容とプロンプトの整合を親が確認する。
- **reviewerの差し戻しは1往復まで**。2回目のNGは親にエスカレーションする。
- **ADRの前提が崩れた場合**: 黙って逸脱させず、`adr` スキルでのADR更新を提案する。
- **サブエージェントが自分のworktree外（親のメイン作業ディレクトリ等）を操作した形跡が
  見つかった場合**: 親は直ちに `git branch --show-current` 等で自分の作業ディレクトリの
  状態を確認し、意図しないブランチ切り替えやマージが起きていないか点検する。起きていた
  場合は元のブランチに戻し、実害の有無をユーザーに報告する（実装内容自体の可否とは別に
  必ず報告する）。

## 全タスク完了時

計画書の全タスクが完了したら `next` スキルと同様、計画のステータス更新や
関連ADRの `承認済み` への更新提案を行う。
